# All-guide dialogue rollout acceptance

The new `rollout-cases.json` corpus contains three six-turn conversations for each of the six production games: 18 conversations, 108 turns. Its frozen pre-run raw SHA-256 is `41fb5ca1d30465a3aa98c8a8d0946f44a3378884deff3cacfadf8a20827f35d1`. The original prototype training, validation, evaluation, follow-up, and consultation files remain unchanged.

Every supported answer has a canonical source-record identity, fixed meaningful excerpts, and exact indexed variant quotation/provenance. These expectations were authored from the trusted `load-records.mjs` declarations/current adapters, the reviewed StarCraft source-record snapshot, and the existing approved conversation/source fixtures. They were not derived from the rollout wrapper, classifier predictions, or runtime answers. All fixed excerpts were checked against the recorded source quotations before running the suite. The source inventory was read through the existing installed Node runtime; nothing was installed or downloaded.

This is source-based integration/regression evidence, not blind organic-user accuracy. It was authored after the prototype design and earlier known failures, and includes the reported SCHNAIL → download-link flow deliberately. Some phrases and subjects also occur in earlier training or tests. Success or failure of a conversation cannot be presented as an unbiased model-accuracy percentage. Frozen factual oracles must not be relabeled to improve a score.

## Input and oracle boundaries

Actual inputs are each turn's `text`, explicit `action`, and an allowlisted `pageAction` where declared. `resetTopic` means a real New topic button click. The one U6 marker action invokes the real page `openSeerForMarker('Iolo')`; its `inputContext` documents that deliberate UI selection. It is actual view context, not an entity inferred from an expected answer. Unknown subsequent names must still not fall back to that atlas selection. The browser harness never feeds `intent`, `supported`, `entityId`, source record IDs, expected text, or expected transitions into the classifier or conversation state.

The `intent` label describes what information is requested, even when unsupported. `supported: false` with `requireDecline` requires the actual proposed response to avoid a factual answer. Resolving a known subject does not establish a requested numeric value, platform, edition, motive, or acquisition facet. Restrictions are actual natural-language requests and must carry into later fragments; a source conflict cannot be resolved by choosing a convenient variant.

The corpus covers:

- Albion crew identity/location/stats, item use/location/acquisition, topic changes, real reset, unindexed subjects, and cross-game qualification.
- Ultima V starting companions, spell spacing, item use, unsupported platform carry, guide-only research exclusion, and pronoun reset.
- Ultima VI companion roles/stats/coordinates, equipment acquisition, a real atlas context, unrelated names, and false-premise motives.
- Al-Qadim items, sword-move spacing and subject changes, unavailable exact damage, explicit reset, a conflicted item, and guide-only rule-book research.
- Ultima VII companion follow-ups, joined/spaced Time Lord, Guardian as a new subject, party-role consultation, unsupported companion download, guide-only identity, and Serpent Isle exclusion.
- StarCraft client/download/install/prerequisite/documentation distinctions, the established Remastered consultation, conflicting launcher compatibility, wrong-subject reset, bot spacing and attribution, guide-only BWAPI definition, and unsupported numerical guarantees.

## Node and browser checks

`rollout-dialogue.test.mjs` exercises the new shared production `createConversationAssistant` API over actual current game source records. Its classifier is explicitly synthetic, based on a few fixed request-syntax categories, and never reads the corpus's expected labels/entities/records. Those tests verify wrapper/source-engine continuity and reset/qualification boundaries. They do not establish learned-classifier quality. The uncertainty case verifies the rejected inference packet, not an invented route-name convention.

`rollout-browser.py` runs all corpus conversations through the actual production UI on seven surfaces (all six games and Al-Qadim's second Walkthrough pane). The Al-Qadim corpus runs on each pane, producing 126 corpus-turn checks. The actual packaged MiniLM intent worker is untouched. A transparent subclass calls the browser's original Worker constructor/postMessage and observes load/classify/result events. Only the previously approved *generative* model worker uses its existing explicit fixture. This is real MiniLM encoder/head inference plus the real source UI/engine; it is not native generative-model evidence.

At each surface the harness also checks desktop 1280×900 and phone 390×844 layout, direct source facts, actual composer hit testing, conversation scrolling, and the absence of removed help selectors/badges. The Ultima VII default dialog must be at least 900px wide with an 800px conversation area at desktop and a usable chat height, proving a materially roomier conversation than the reported narrow modal. The native Expand chat dialog must preserve the same source conversation, accept five more real sends, allow wheel scrolling, close via Escape, restore the guide view, and accept another source-checked send. These checks use actual controls and nodes; no replacement UI is mounted.

The script starts its own loopback static server on port 0 and shuts down only that server. It blocks outside requests, non-GET methods, request bodies, and service workers. It records actual requests, browser errors, source hashes, frozen corpus hash, explicit storage mutations, before/after storage snapshots, native intent-worker evidence, per-turn replies, and layout geometry. Saved-game writes are forbidden; only the explicit consent preference write is allowed. New result tags preserve old reports rather than overwrite them.

Expected record IDs remain honestly labeled oracle metadata when the UI does not expose them; actual rendered source citations are checked against reviewed provenance. No production module is rewritten or injected to fabricate a record observer. Runtime source metadata is never used to create the expected claims.

Reports are `guides/tests/assistant/evidence/rollout-browser-<tag>.json`; representative Sage screenshots are placed under the already ignored `intent-prototype/results/rollout/<tag>/`. Exploratory failures must remain visible and be reported as source/intent/state/layout issues. A runtime change can justify a new run, not a weakened expected fact.

## Probe and source-oracle audit revision

The preserved native-MiniLM exploratory run `evidence/rollout-browser-rollout-probe.json` completed all seven surfaces: 82/126 original corpus-turn checks passed, with native load/classify/result evidence on every page. Thirteen of fourteen desktop/phone/expanded layout checks passed. The roomier default Sage measured 1152px dialog width, 1096.8px conversation width, and 571px conversation height at desktop; the phone Send control was obscured by Assistant settings. No page errors, external requests, or saved-game writes occurred; all requests were static GETs. Source-hash stability intentionally failed because `dialogue.js` and `source-responses.js` changed during the exploratory run. This is preserved as exploratory evidence, not a final stable-source pass.

The majority of failed supported turns still received correct top MiniLM relation labels but were blocked by unrecognized material, relation-fragment grammar, or overbroad reset/consultation routing. Some model top labels were wrong, and the report preserves those too. No expected fact was changed to conceal those failures. A full request/prediction/failure map was sent to the dialogue implementation owner.

After the probe, the parent explicitly approved this independently source-justified oracle audit:

1. The generic Al-Qadim request “his location” for Zubakon can legitimately return the independently indexed city **Bandar al-Sa'adat** (`alqadim:npc:zubakon:location`, `guides/js/AlQadimAtlasData.js`) or the independently indexed **shop with no sign** (`alqadim:topic:zubakon-shop:location`). The original oracle incorrectly demanded the more specific shop even though the user did not ask which shop. The unchanged original expectation remains the first branch, and an exact city/source alternative was added as a separately witnessed branch. The question was not narrowed to fit the original answer.
2. The StarCraft consultation already returned the correct map, Use Map Settings, and SCHNAIL alternative. Its planner deliberately used a declared lower-tier source variant at the direct ceiling. The original harness demanded only the direct variant's physical extraction source, excluding that same record's legitimate authored-overlay variant provenance. Exact static source/quote variants of the two already-reviewed records were added as allowed provenance; factual excerpts and record identities stayed unchanged. These variants were copied from the indexed source record before the next model run, not inferred from the rendered citation.

The original frozen corpus hash remains `41fb5ca1d30465a3aa98c8a8d0946f44a3378884deff3cacfadf8a20827f35d1`, and the original report is retained. The audited revision 2 raw SHA-256 is `e804a7ffde69500e8e71e891a6347ce0c212fa2134239cf3a59b09c07dae6570`. The new `answerAlternatives` branches couple each allowed factual excerpt to its own exact evidence; the harness does not accept a city fact with unrelated shop evidence. `sourceVariants` permits only exact predeclared variants of the same canonical source record. A new run is required before reporting revised pass counts.
